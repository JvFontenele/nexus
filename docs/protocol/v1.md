# Protocolo Nexus v1 (rascunho para revisão)

## Transporte
- TCP, porta padrão **47210** (configurável). TLS 1.3 obrigatório (`minimum_version = TLSv1_3`).
- Cada dispositivo tem uma identidade persistente: par de chaves EC P-256 + certificado X.509 autoassinado (CN fixo `nexus`, validade de 10 anos; o CN não pode ser o device_id, que é o hash do próprio certificado). **device_id** = SHA-256 hex do DER do certificado (fingerprint).
- O PC (`nexusd`) é sempre o servidor; Android e outros PCs se conectam como cliente.
- O cliente fixa (pin) o fingerprint do servidor após o pareamento. Antes do pareamento, aceita qualquer certificado, mas a confirmação do código (abaixo) cobre um ataque MITM.
- Autenticação do cliente: mTLS. O servidor usa `CERT_OPTIONAL`, carregando como âncoras só os certificados de clientes já pareados.
  - Cliente pareado: apresenta o certificado, que é verificado pelo TLS.
  - Cliente não pareado: conecta **sem certificado** e só pode enviar `hello` e `pair.*`.
  - Certificado desconhecido: o handshake falha.
  - **A autoridade é o `trusted.json`, não o handshake:** após o TLS, o servidor busca o fingerprint do peercert no store (`lookup_der`). Uma conexão aberta com um `SSLContext` antigo, de antes de uma revogação, passa a ser tratada como não pareada.
  - O `hello.cert_pem` precisa ter exatamente um certificado, ser X.509 válido (parseado pelo OpenSSL) e ter fingerprint igual ao `device_id`; senão `bad_body`.
  - **E1 (2026-10-24, Python 3.12, OpenSSL do sistema):** validado com certificados EC P-256 autoassinados. Cliente pareado → ok, peercert presente; sem certificado → ok, peercert `None`; certificado desconhecido → `SSLCertVerificationError`.
  - A geração do certificado usa o `openssl` CLI (`req -x509 -newkey ec`), porque a stdlib do Python não gera certificados.

## Framing
- Cada mensagem é 4 bytes big-endian com o tamanho, seguidos de JSON UTF-8. Máximo de **1 MiB** por mensagem; acima disso, a conexão é fechada.
- Envelope: `{"v":1,"id":"<uuid4>","type":"<tipo>","body":{...}}`. Respostas levam `"re":"<id>"`.
- JSON inválido, `v` diferente de 1, campo obrigatório faltando ou tipo errado: responde `error` e conta como falha. Com 5 falhas, a conexão é fechada.
- Timeout de inatividade de 90 s; o cliente envia `ping` a cada 30 s.
- Limite de 50 mensagens/s por conexão.

## Tipos (v1)
| type | direção | body | pré-condição |
|---|---|---|---|
| `hello` | C→S, S→C | `{device_id, name, kind: "phone"\|"tablet"\|"pc", app_version, protocol: [1]}` | nenhuma |
| `pair.request` | C→S | `{commit}` | não pareado; máximo de 3 por minuto por IP |
| `pair.challenge` | S→C | `{session, n_s, expires_in: 60}` | — |
| `pair.reveal` | C→S | `{session, n_c}` | — |
| `pair.confirm` | C→S | `{session, accept: bool}` | — |
| `pair.result` | S→C | `{ok: bool, reason?}` | — |
| `unpair` | ambos | `{}` | pareado |
| `ping` / `pong` | ambos | `{}` | pareado |
| `actions.list` → `actions.result` | C→S | `{}` → `{actions:[{id, description, params, phone_safe}]}` | pareado; só lista `phone_safe` |
| `action.run` → `action.result` | C→S | `{action, params}` → `{ok, result?, error?}` | pareado; ação `phone_safe` e permitida para o dispositivo |
| `share.text` | ambos | `{text}` (máximo 64 KiB) → `action.result{ok, result:"copiado"\|"notificado"}` | pareado; no PC: wl-copy + notificação |
| `clipboard.set` | ambos | `{text}` (máximo 64 KiB) | pareado; opt-in por dispositivo |
| `open.url` | S→C | `{url}` (só http/https) | pareado; o telefone mostra uma notificação e só abre ao toque do usuário |
| `error` | ambos | `{code, message}` | — |

Tipo desconhecido: responde `error{code:"unknown_type"}` sem derrubar a conexão.

## Pareamento (SAS com commit/reveal; revisão #005)
Notação: `fp_s`/`fp_c` = fingerprints dos certificados vistos **no próprio handshake TLS** (o do cliente vai no `hello.cert_pem` e o servidor confere se a chave pública dele bate com a que o cliente usa em seguida; v1: o cliente reconecta com mTLS após o pareamento e o servidor confere `fp_c`). `H` = SHA-256.
1. `pair.request` (C→S): `{commit: hex(H(n_c ‖ fp_c ‖ fp_s))}`, com `n_c` = 32 bytes aleatórios (`secrets`). O cliente se compromete **antes** de ver o nonce do servidor.
2. `pair.challenge` (S→C): `{session: uuid4, n_s: hex(32 bytes), expires_in: 60}`.
3. `pair.reveal` (C→S): `{session, n_c}`. O servidor confere o commit; se não bater, aborta e conta como falha.
   Codificação: `n_c`, `n_s`, `fp_c`, `fp_s` entram no hash como os 32 bytes crus (hex decodificado), e `session` entra como UTF-8. Todos os campos têm tamanho fixo, exceto `session`, que fica entre o prefixo e o sufixo fixo, então a concatenação não é ambígua. Implementação: `nexus/proto/pairing.py`.
4. Os dois lados calculam o código = `int(H("nexus-pair-v1" ‖ session ‖ fp_s ‖ fp_c ‖ n_s ‖ n_c)[:8 hex], 16) % 1_000_000`, com 6 dígitos, e mostram ao usuário. O PC mostra uma notificação com o nome e o código; o telefone mostra o mesmo código e o fingerprint curto do PC.
5. `pair.confirm` (C→S `{session, accept}`) e confirmação local no PC. As duas são exigidas em até 60 s.
6. Com as duas confirmações, `pair.result{ok:true}`. O PC grava `{device_id, name, kind, cert_pem, paired_at, permissions: []}` em `~/.local/share/nexus/trusted.json` (0600, escrita atômica com tmp + `os.replace`), monta um **novo** `SSLContext` com as âncoras atualizadas e troca a referência de forma atômica (as conexões existentes ficam intactas). O cliente pina `fp_s`.
- O código é invalidado ao expirar, falhar, desconectar ou ser usado uma vez. Só um pareamento pendente por conexão e por IP.
- Por que commit/reveal: com nonce só do servidor, um MITM vê `n_s` e pode gerar certificados em série até casar 6 dígitos (~10⁶ tentativas em 60 s, viável em paralelo). Com o commit, ele precisa fixar `n_c` antes de ver `n_s`, e a chance cai para 1 em 10⁶ por tentativa de pareamento (limitado a 3/min).
- Primeiro contato: o nome mDNS e o IP nunca são prova de identidade. Só o SAS (ou o QR com `id=fp_s`) prova.
- **Revogação:** `nexus devices revoke <id>` remove o registro, troca o `SSLContext` e **fecha as conexões ativas** daquele `device_id`.

## Replay e concorrência
- O `id` de mensagem é único por conexão; `id` repetido → `error{code:"replay"}`. TLS já impede replay entre conexões.
- Máximo de 8 conexões simultâneas, 1 por `device_id` pareado (a nova substitui a antiga).

## Autorização de ações
- O telefone nunca envia comando de shell, só o `action` id do catálogo, com params validados por `parse_params`.
- Só ações `phone_safe=True` são listadas e executáveis remotamente. `dangerous` nunca é remota na v1.
- `permissions` por dispositivo: lista de ids permitidos, ou `["*phone_safe"]`. Padrão após o pareamento: vazio. O usuário libera com `nexus devices allow <id> <action>`.
- Todo `action.run` remoto entra no log com `device_id`, mas nunca com os valores dos params.

## Descoberta
- mDNS/DNS-SD: `_nexus._tcp.local`, TXT `id=<device_id>`, `name=`, `v=1`. Fallback: IP/host manual e QR code com `nexus://<host>:<port>?id=<device_id>`.
- Pela tailnet: IP manual (100.x). O protocolo é o mesmo.

## Modelo de ameaças (resumo)
| Ameaça | Mitigação |
|---|---|
| Dispositivo desconhecido na LAN | Só `hello`/`pair.*`; pareamento exige confirmação humana nos dois lados; rate limit |
| MITM no pareamento | Código SAS derivado dos dois fingerprints |
| Celular perdido | `revoke` no PC; ações remotas são só `phone_safe` com allowlist |
| Certificado/chave roubados | Revogação; chave do PC em 0600; rotação = novo pareamento |
| Comando injetado | Sem shell; catálogo com params tipados; sem interpolação |
| Mensagem gigante ou fuzz | Limite de 1 MiB, validação de esquema, fechamento após 5 erros |
| Rede pública | Só a LAN privada e a tailnet; o daemon escuta só nas interfaces configuradas (padrão: LAN + tailscale0) |
| Sessão abandonada | Timeout de 90 s; reconexão exige o mesmo certificado pinado |

## Testes negativos obrigatórios antes de liberar a v1 (revisão #005)
MITM com certificados trocados (códigos divergem); commit que não bate com o reveal; certificado desconhecido no handshake; replay de `id`; confirmação após expirar; confirmação reutilizada; revogação com conexão ativa (precisa cair); `action.run` de ação não `phone_safe`, não permitida ou com parâmetros maliciosos (`;`, `$(…)`, path traversal); mensagem > 1 MiB; 5 mensagens inválidas → fecha.

## Implementação Linux (T02c, consulta #006)
- `nexus daemon` (`nexus/daemon.py`): asyncio. Aceita TCP puro e faz `start_tls` com o `SSLContext` **vigente** em cada conexão; assim a troca de contexto vale para o próximo handshake sem reiniciar o servidor.
- Interfaces padrão: IPv4 privados e CGNAT (tailnet), ignorando `lo`, `docker*`, `br-*`, `veth*` e `virbr*`. Para sobrescrever: `--listen ip1,ip2`.
- Canal de controle local: socket Unix `$XDG_RUNTIME_DIR/nexus/control.sock` (diretório 0700, socket 0600, uid conferido por `SO_PEERCRED`). A CLI o usa em `nexus pair pending|confirm|reject` e `nexus devices list|revoke|allow`. O `confirm` mostra o nome, o fingerprint completo e o código, e pede confirmação.
- Depois do `pair.result{ok}`, o cliente fecha e reconecta com mTLS. A conexão do pareamento continua não pareada.
- PC → dispositivo (A03): o dispositivo mantém a conexão aberta (ping a cada 30 s). `nexus` envia `share.text`/`open.url` por ela, via `Command{cmd: "send.text"|"open.url", device_id, …}`. São mensagens sem resposta: o dispositivo não responde a pushes.
- Remotamente, não são aceitas ações com parâmetro do tipo `path` nem chaves de params contendo `=`.
- mDNS: Avahi via D-Bus (`nexus/mdns.py`). Se o Avahi faltar, o daemon segue sem descoberta. O cliente trata nome, IP e TXT como dados não confiáveis.
